# The Pangea native shell

The shell turns a Pangea project (a Faust sound module, optionally a plain C++ logic module, and a `plugin.json`) into an Audio Unit (`.component`) and a VST3 (`.vst3`) on the user's own Mac. It is one JUCE 8 plugin written once by the platform; the project supplies the sound. A MIDI tool (`kind: "midi"`, `docs/midi-tools.md`) makes no sound: its logic module plays notes into another instrument, and it builds as two plugins (see "MIDI tools" below). The desktop app runs `build.sh`; people never see it.

## The Pangea plugin

`build-host.sh [--install] [--check]` builds the Pangea plugin (`docs/pangea-plugin.md`): Pangea, Pangea Instrument and Pangea MIDI FX, which open any of the member's projects as a module and follow new versions without a rescan. `build-module.sh <project dir> <module dir> [--allow-logic]` compiles one version into a module (`platform/PangeaModule.cpp`, `platform/PangeaModuleApi.h`), an instrument's effect section with it; the desktop app runs it. The plugin is `platform/PangeaHost.h`; `tools/test-host.sh` runs `tools/host-check` on real modules of every kind (`build-host.sh --check`). After its 128 parameter slots it has one more parameter, Pangea's bypass, which works as it does in a built plugin (see "The bypass").

## Building a project

```
shell/build.sh <project dir> [--install] [--verify] [--clean] [--no-auval] [--allow-logic] [--native-editor]
```

- `--install` copies the plugins into `~/Library/Audio/Plug-Ins/Components` and `~/Library/Audio/Plug-Ins/VST3`, restarts `AudioComponentRegistrar` so Logic sees the change, and runs `auval -v aufx|aumu <code> Pnga`. The build fails if validation fails. A MIDI tool installs both its components and its VST3, and both are validated: `auval -v aumu <pluginCode> Pnga` and `auval -v aumi <fxPluginCode> Pnga`.
- `--verify` also builds `pangea-render`, renders a few seconds through the processor (MIDI for instruments, a test signal for effects, a playing transport at 124 BPM for logic modules), writes `build/<slug>.wav`, loads the VST3 in a JUCE host and renders through it, and draws the interface to `build/<slug>-editor.png`. Silence or a load failure fails the build. An instrument with an effect section is also put through `pangea-render effect-check` (see "An instrument's effect section"). A MIDI tool makes no sound, so there is no audio check: `pangea-render notes` runs the processor offline and `pangea-render host-check` loads the VST3 (see "MIDI tools"); a failure of either fails the build. Every kind is also put through `pangea-render bypass-check` (see "The bypass"): a plugin whose bypass does not do what a bypassed plugin does fails the build.
- `--clean` starts from an empty `build/` (the next build compiles JUCE again).
- `--no-auval` installs without validating.
- `--native-editor` draws the interface with the shell's own editor (`platform/PangeaEditor.h`), the older panel. Without it the interface is the component library's, drawn in a web view (`platform/PangeaWebEditor.h` and `platform/web/`): the panel the builder shows (`docs/decisions.md`, decision 77). `--web-editor`, the name it had as a test, is still taken. The build's last line says which was built: `"editor": "web"` or `"native"`.
- `--allow-logic` is required for a project that carries `logic.cpp`. Without it the build is refused before anything compiles. The desktop app passes it only for the signed-in user's own projects (`docs/decisions.md`, 17).

Progress lines go to stdout as the build runs. The last line is always one JSON object, for example:

```
{"ok": true, "stage": "done", "name": "Tape Drift", "slug": "tape-drift", "kind": "effect", "version": "0.1.0",
 "pluginCode": "Tpdr", "manufacturerCode": "Pnga", "bundleId": "com.pangea.tape-drift", "logic": false,
 "component": "/Users/me/Library/Audio/Plug-Ins/Components/Tape Drift.component",
 "vst3": "/Users/me/Library/Audio/Plug-Ins/VST3/Tape Drift.vst3",
 "installed": true, "auval": "passed", "auvalLog": ".../build/auval.log", "verify": "passed",
 "faust": "2.88.0", "faustExpected": "2.88.0", "juce": "8.0.10", "firstBuild": false, "seconds": 24}
```

A MIDI tool's line also names its second plugin and its validation:

```
{"ok": true, "stage": "done", "name": "MIDI Steps", "slug": "midi-steps", "kind": "midi", ..., "pluginCode": "Mstp",
 "component": "/Users/me/Library/Audio/Plug-Ins/Components/MIDI Steps.component",
 "vst3": "/Users/me/Library/Audio/Plug-Ins/VST3/MIDI Steps.vst3", "auval": "passed", ...,
 "fxPluginCode": "Mstx", "componentFx": "/Users/me/Library/Audio/Plug-Ins/Components/MIDI Steps FX.component",
 "auvalFx": "passed", "auvalFxLog": ".../build/auval-fx.log"}
```

Effects and instruments have no `componentFx` or `auvalFx`. An instrument's line says what became of its effect section: `"effectSection": "built"`, `"none"` (its code defines no `effect`) or `"left out"` (it does not compile, with the compiler's words in `"effectSectionError"`). On failure `ok` is false, `stage` says where it stopped (`tools`, `project`, `check`, `faust`, `logic`, `configure`, `build`, `verify`, `install`, `auval`) and `error` says why. The exit code is 1.

### When Faust does not finish

Every Faust compile has 120 seconds (`FAUST_TIME_LIMIT` in `tools/run-faust.sh`, Faust's own default for `-t`). At the limit Faust stops itself with an alarm: it ends on signal 14, the shell sees exit status 142, and Faust writes nothing. The build then fails at the `faust` stage and says so, naming the file the project gave:

```
{"ok": false, "stage": "faust", "error": "Faust 2.88.0 stopped at its time limit of 120 seconds before it had finished compiling /Users/me/Library/Application Support/Pangea/host/sources/<projectId>/v4/dsp.dsp.", ...}
```

Faust stopped by another signal says which ("was stopped by signal KILL"), and Faust that fails with no words gives its exit status. A compile error is reported as before, `faust failed:` and the compiler's words. Until 13 November 2026 a compile stopped at the limit was reported as `faust failed: ` and nothing more. `build-module.sh` adds about a second of clang to Faust's time, and the Pangea plugin waits 180 seconds for an answer (`kRequestTimeoutSeconds` in `platform/PangeaHost.h`), so the member reads this message and not "The Pangea app did not answer".

Every compile also has `-sn`, Faust's simple names (decision 78). Faust 2.88.0 names every call of a function, for its diagrams, by writing the call's argument out as text, and an argument that holds the same parts many times is written out in full each time, so the text can double at every level. Drum Forge, a drum voice whose mod matrix passes its oscillators' outputs into every slot, took 374 s that way and never built; with `-sn` it builds as a module in 13 s. The C++ Faust writes is the same byte for byte with and without it (146 versions compared). Only the names in Faust's own error messages are shorter: `g(hslider("x", ...))` becomes `g`. The browser's Faust (2.90.19) bounds that text itself.

What the Mac needs: Xcode or the Command Line Tools, `cmake`, `ninja`, `faust` (Homebrew), and JUCE 8.0.10 at `shell/JUCE` (`git clone --depth 1 --branch 8.0.10 https://github.com/juce-framework/JUCE shell/JUCE`). The Faust architecture headers are taken from `<faust prefix>/include`. `build.sh` names whatever is missing.

## The project directory

```
plugin.json   { "name", "slug", "kind": "effect" | "instrument" | "midi", "bundleId": "com.pangea.<slug>",
                "manufacturerCode": "Pnga", "pluginCode": "Xxxx", "version": "0.1.0", "description" }
              a MIDI tool adds "fxPluginCode": "Xxxx" (not the same as pluginCode) and, optionally,
              "fxBundleId" (default "<bundleId>.fx", which must differ from bundleId)
dsp.dsp       the Faust source; effects are stereo in and out, instruments declare
              declare options "[nvoices:8]"; and use freq, gain and gate, and may define
              effect = ...; beside process, one stage for all the voices; a MIDI tool has the
              platform's silent program, declare name "<name>"; process = 0, 0;
logic.cpp     optional, a struct Logic following platform/logic_api.h; required for a MIDI tool
ui.json       optional, the interface: src/lib/ui/schema.ts (see "The interface" below)
```

`pluginCode` (and a MIDI tool's `fxPluginCode`) is four characters with an upper case first character, stable for the life of the project. `version` must change for Logic to notice a rebuilt Audio Unit; the shell puts it in the bundle and the AU component version.

How the Faust code maps to the plugin:

- Each `hslider`, `vslider`, `nentry`, `checkbox` and `button` becomes a plugin parameter. Its id is the label in lower case without punctuation (`Env Amount` becomes `envamount`), so automation in Logic survives rebuilds as long as the label stays. Two controls with the same label fall back to the full path.
- `[unit:x]` is shown next to the value, `[scale:log]` makes the range logarithmic, `[hidden:1]` hides a control, `[logic:1]` hands it to the logic module. Sliders and number entries are knobs, check boxes are switches, buttons are switches that are on while held (`[style:knob]` changes nothing).
- An instrument is polyphonic when the code declares `[nvoices:N]` and has `freq` (or `key`) and `gate` controls. Then the shell wraps `mydsp` in Faust's `mydsp_poly` with N voices (voice allocation, stealing with a short crossfade, release detection at -90 dB) and drives it from the host's MIDI: note on and off at their exact sample, sustain pedal, all notes off. `gain` receives velocity divided by 127. An instrument without `[nvoices:N]` (the acid line) runs one `mydsp` and is played by its logic module from the host transport.
- Effects with one input hear the average of both channels; one output is sent to both sides. Mono and stereo host layouts both work.
- Every plugin has one parameter more than its code and its logic module give it: Pangea's bypass, `pangea_bypass`, named Bypass, always the last (see "The bypass").

## The bypass

Every Pangea plugin has one bypass, and Pangea supplies it: the model that writes a plugin's sound never writes one for the whole plugin, and the Faust code and the logic module know nothing of this one (decisions 74 and 75). It is the same in a plugin built for one project (`HybridShell.cpp`) and in the Pangea plugin (`PangeaHost.h`), from one header, `platform/PangeaBypass.h`.

- **One parameter.** Its id is `pangea_bypass`, its name is Bypass, it is off in a new plugin and it is always the last parameter. No project's code can make that id: a Faust control's id is its label in lower-case letters and digits, and a logic control's is `logic` and a number, so neither has an underscore. A control the code labels Bypass has the id `bypass` and is another parameter, and a host then shows two of that name.
- **The host's bypass.** The processor answers `getBypassParameter` with it. So the VST3 tells the host that it is the bypass (`kIsBypass`), and the Audio Unit's bypass property and the parameter move each other. A host whose own bypass button tells the plugin switches this parameter. A host whose button only stops calling the plugin tells it nothing: there the button on the panel and the host's button are two things. JUCE's wrappers never call `processBlockBypassed` for a plugin that has a bypass parameter, so the parameter is read in `processBlock`; `processBlockBypassed` is kept, and does the same, for a host that calls it all the same.
- **In an Audio Unit's list** it comes after every other parameter: its version hint is 3, where a control has 1 and a control only an instrument's effect section has has 2. Logic and GarageBand keep automation by a parameter's place in that list, so a plugin built again keeps the places it had.
- **Every switch is a fade of 30 ms**, counted in samples (1440 at 48 kHz), so it never clicks. The gain moves by one step a sample towards what was asked for, and a switch taken back inside a fade turns round where it stands. What is asked for first after the host prepares the plugin is taken at once: a session that opens bypassed starts bypassed.
- **An effect** gives its input, to the bit, once the fade is over: a copy of the host's input is kept before the plugin's output overwrites it. A mono input on a stereo output goes to both sides, and a stereo input on a mono output is the mean of its two sides. The Faust code runs on unheard, as it does in the builder, so the effect comes back with its tails as they are. The cost is that a bypassed plugin takes the processor time it takes when it is in.
- **An instrument** fades to silence. It takes no new notes from the moment the bypass is asked for; note offs, the pedal and all notes off still pass, so a note begun before the bypass can end inside the fade. Once the fade is over every voice is ended, once, by the path a MIDI all notes off takes, and rings out unheard. Taken off again inside the fade, the notes play on. With the bypass off, the next note plays.
- **A logic module** in an effect or an instrument is run, while bypassed, the way it is run while the transport is stopped, with the song carrying on underneath: it ends its notes, starts none, and comes back in time. **A MIDI tool** is transparent while bypassed, as before: its own notes end where the bypass begins, it starts none, the MIDI it is sent passes through, and the notes that passed are ended where the bypass ends (see "MIDI tools").
- **Saved with the plugin**, beside its other parameters. A state saved before the plugin had its bypass says nothing of it and opens with the plugin in.
- **With the plugin in and no fade running**, nothing is done for the bypass: a block is the plugin's own, sample for sample.
- **On the panel** it is a switch at the far right of the title row (see "The interface"). With the web panel (`--web-editor`), it is the button at the far right of the library's header bar, as in the builder.

`pangea-render bypass-check [--vst3 <plugin.vst3>]` plays the processor, and with `--vst3` the built plugin loaded as a DAW loads it, with the bypass on before the first block and switched in the middle. The plugin's own render of the same run and its input are known, so every sample is held: the render to the bit where the plugin is in, the input (or silence) to the bit where it is bypassed, and the mix of the two inside each fade, with no step larger than the fade allows. It also checks the parameter (its id, name, place and version hint, and in the VST3 that the host is told it is the bypass, under the plugin's own id and not JUCE's), that an instrument has no voice holding a note once the fade is over and takes none while bypassed, that a MIDI tool is transparent, that a logic module is run as stopped, that `processBlockBypassed` gives the same, and the state both ways. `--verify` runs it for every kind. `tools/test-bypass.sh` has the rest (its first lines say which), and `tools/test-host.sh` checks the same in the Pangea plugin, with its web panel.

## The sidechain

An effect may listen to a second sound: the kick that ducks a pad, the drums that open a gate (`docs/sidechain.md`). Its Faust code says so with one line, `declare sidechain "stereo";` (two inputs after the sound's two) or `declare sidechain "mono";` (one), and the site holds the inputs to it before a version is saved.

- **The buses.** Such an effect has a second input bus, Sidechain, stereo, and off by default (`withInput (..., false)`). In a VST3 it is an auxiliary bus that is not active by default, so the host is told two inputs and two outputs until it routes a track there. An Audio Unit has no bus that is off: JUCE's wrapper switches every bus on, so the Audio Unit has a second input element, which is what Logic's Side Chain menu looks for, and it hears silence until a track is chosen there. The bus takes off, mono or stereo, whatever the main bus is, and nothing else.
- **What the code hears.** Its inputs after the sound's two are fed from the bus: as they are, a mono bus on both sides of a stereo sidechain, a stereo bus as the mean of its sides on a mono one, and silence while the bus is off (`fillSidechain`). Only the main bus is a bypassed effect's input, and only the main bus is what an effect with no sidechain reads.
- **Without the line** a plugin has exactly the buses it had: one input, Input, and one output, Output, both stereo and on. Its parameters and its state are as before: Tape Drift built with this shell and with the one before it shows a host the same seven parameters, defaults and steps, and the same state, byte for byte (`pangea-render describe-vst3` on both).
- **The Pangea plugin** has the bus whatever it opens (`docs/pangea-plugin.md`, "The sidechain input"), so it is version 0.3.0.

`pangea-render sidechain-check [--vst3 <plugin.vst3>] [--wav <out.wav>] [--expect-duck <dB>]` checks the buses, with and without a sidechain, and for an effect that declares one plays a held pad with the sidechain off, on and silent, with a kick on every beat in stereo and in mono, and through the built VST3 with its sidechain switched on as a host does it. It writes the keyed render with `--wav`, for listening. `--verify` runs it for every effect.

## An instrument's effect section

An instrument's Faust code may define `effect = ...;` beside `process`. `process` is one voice; `effect` is one stage that all the voices share, where the delay, the reverb, the output level and the safety clip usually go. The builder plays it (faustwasm compiles `effect` as a second program and runs it on the mixed voices), so the plugin does too (decision 73).

- **The build.** For an instrument, `build.sh` and `build-module.sh` run `tools/build-effect.sh` once the voice has compiled. It puts the same copy of `dsp.dsp` inside an environment and compiles `effect` as class `mydsp_effect` in `FaustEffect.h`, with the voice's Faust options. The program it compiles is `effect/dsp.dsp` in the generated folder. It has the voice's file name because Faust names the root group of a program that declares no name after its file, and the voice and the effect must agree on their root for a control both read to have one address. The few names that program defines for itself carry a hash of the source, so no source can use them: an effect that names one does not compile here, as it does not in the builder. Only an instrument is looked at: an effect plugin or a MIDI tool whose code names something `effect` builds as it always did.
- **The channels** are fitted as faustwasm 0.20.0 fits them. The voices' outputs go to the effect's inputs as they are when the counts match, split when the effect takes more and summed when it takes fewer. The effect's outputs are followed by silent channels up to the widest of the three counts. A stereo voice into a stereo effect, the usual shape, is two channels straight through. An effect that gives more channels than a plugin carries (eight, `kMaxFaustChannels`) is left out, and the build says so.
- **The sound.** The shell runs the effect on the mixed voices inside the slice loop, through Faust's own `dsp_sequencer` (what its polyphonic architecture uses, `faust/dsp/poly-dsp.h`), which holds the voices' mix in a buffer of its own, one slice long. Nothing is allocated while it plays. A mono instrument (no `[nvoices:N]`) runs its one voice into the effect the same way.
- **The controls** of the effect are plugin parameters, after the voice's, in the order the site stores them. Their ids are made as every id is made (the label, or the full path when a label repeats); an effect control whose full path is the id of a voice control already, a different definition at the same address, has `effect` after it, so a parameter of the effect never shares an id with another. In an Audio Unit's list the effect's own parameters come after all the others (version hint 2, where every other parameter has 1): Logic and GarageBand keep automation by a parameter's place in that list, so an instrument that was built before its effect section was in the plugin keeps the places of the parameters it had. Their layout keys are the site's: the labels of the groups below the root and the control's own label, whichever of the two programs the control lives in, so a layout made on the site places them. In the automatic arrangement the effect's groups follow the voice's, and a group with the label of one the voice has is that group.
- **A control the voice and the effect both read** (one definition, used by both: the same address, kind, range and start) is one parameter that sets both. Two controls that only share a key stay two parameters, each at its own start: a Trim from 0 to 1 in the voice and a Trim in decibels in the effect, or a Level at the top of the voice and a Level in an effect whose only group Faust has made its root (a key leaves the root out, an address does not). The panel shows the first, as the web panel does. A control marked `[pangea:bpm]` follows the host's tempo wherever it lives, as do `[pangea:playing]` and `[pangea:beat]` (decision 123) and `[pangea:beatfrac]` (decision 124), and a `[logic:1]` control may live in the effect, where the logic module drives it beside one of the same label in the voice.
- **An effect that does not compile** is left out: the builder plays such an instrument with its voices alone, so the plugin does too. The build says so in a warning line and in its last line (`"effectSection": "left out"`, with the compiler's words in `"effectSectionError"`). An effect that Faust did not finish, stopped at its time limit or by a signal, is not left out, since that says nothing about the code: the build fails at the `faust` stage and says why ("before it had finished compiling the effect section of .../dsp.dsp"). Until 13 November 2026 such an instrument was built without its effect section, with an empty reason.

`pangea-render effect-check [--vst3 <plugin.vst3>] [--expect <id>]... [--shared <id>]...` lists the effect's controls by key and says where each lives, then plays the same notes with each of its parameters at its lowest and at its highest, one at a time. It fails when a control is not bound to the effect; when the effect has parameters of its own (ones the voices do not read) and none of them changes the render, alone or all together; when those would not come after the other controls in an Audio Unit's list, or Pangea's bypass would not come after them all; and with `--vst3`, when the built plugin lacks one of the effect's parameters by name, or its render does not change when one of the effect's own moves. Only the effect's own parameters count as proof that it is heard: a control the voices read too changes the sound through them, and a render with a sample that is not a number proves nothing. `--expect` names a parameter that must be the effect's and must change the render, `--shared` a control the voices must hold too. `--verify` runs it for every instrument with an effect section. `pangea-render keys` prints the layout key of each parameter, one a line, to hold against the site's. `tools/test-effect.sh` has the other checks (its first lines say which), and `tools/test-host.sh` plays Dub Keys in the Pangea plugin.

## MIDI tools

A MIDI tool (`docs/midi-tools.md`) is a logic module and nothing else: it follows the host's transport and plays notes into another instrument, as an arpeggiator or Pattern Player does. It builds, from the same sources, as the two plugins Pattern Player ships as:

- **`<Name>`** (`PangeaMidi`): an instrument with MIDI out, AU `aumu` and VST3, with silent stereo audio. For Ableton Live and Bitwig: put it on a MIDI track and route another track's MIDI From to it.
- **`<Name> FX`** (`PangeaMidiFx`): an AU MIDI effect, `aumi`, AU only, with no audio buses, its own code (`fxPluginCode`) and bundle id (`fxBundleId`). For Logic's MIDI FX slot.

**MIDI in is dropped.** A MIDI tool plays its own notes. Pattern Player uses held notes as harmony; Two Hands leaves that out, so whatever reaches the plugin is discarded (both plugins accept MIDI, so a host can route to them).

**What the processor does with a version 2 module, every block:**

- **The block:** `bpm`, `ppqStart` and `playing` from the host, and `beatsPerBar` from its time signature (numerator times 4 over denominator: 4 in 4/4, 3 in 6/8), 4 when the host gives none. A host with no position runs freely from the first block.
- **Events by kind:** a `control` of 0 or more sets a sound control, as in version 1 (the shell drops a value that is not a number). `LOGIC_NOTE_ON` and `LOGIC_NOTE_OFF` become MIDI out on their sample in a MIDI tool, with the module's channel, note and velocity; in a polyphonic instrument they play the Faust voices, with the same safety net; in an effect or a mono instrument they are ignored. `LOGIC_DISPLAY` sets one of eight display slots the editor reads (atomics, `PangeaNotes.h`).
- **The safety net** (`PangeaNotes.h`, tested by `tools/test-platform.sh`): it tracks the notes the module has on, per channel and note. Offsets are clamped into the block, notes to 0 to 127, channels to 1 to 16, velocities to 1 to 127 (a velocity that is not a number drops the note), and the events are sorted again, offs first at the same sample. A second on for a sounding note is preceded by its off, and an off for a note that is not on is dropped. While the transport is stopped no note starts. Everything still sounding gets its off at the start of the block when playback stops, when the transport jumps (a block that starts more than 64 samples, plus a sixteenth of the last block, from where the last one led), after a release or a reset (the next block), and when the plugin is bypassed (Pangea's bypass parameter, which the panel's switch and a host's own bypass move; "The bypass"). Bypassed, the tool is transparent: MIDI in passes through, and those notes are ended when the bypass ends. A well made module never needs any of this, and the check before saving fails one that does; `pangea-render notes` says so too.
- **No fused multiply-add:** the module and the platform maths are compiled with clang's `fp contract` off (a pragma around the include in `HybridShell.cpp`; the Faust code is compiled as before), so the plugin rounds as the browser's WebAssembly does, which has no fused instructions.
- **Parameters:** each `LogicParam` is a host parameter with the id `logic<index>`. A control in a group carries the group in the host's name, "Left hand Accent 1", because both of Two Hands' hands have an Accent 1. A menu shows its labels to the host and takes them back when typed; its value stays the number the module reads.

**The checks** (`--verify`):

- `pangea-render notes [bars] [bpm]` runs this build's processor 8 bars at 120 BPM in blocks of 512, then stops: notes must come out, all in range, every one must end and none may be left on. The same notes at blocks of 64, 128 and 480, and every control at its minimum and at its maximum still ends its notes. It prints the first notes, what each display slot showed, and a warning when the module on its own leaves a note on.
- `pangea-render host-check <plugin.vst3>` loads the built VST3 as a DAW would, finds the module's controls among its parameters by name, and drives it with a transport. Its MIDI out must match, note for note and sample for sample, the module run on its own (compiled into the tool from the same source) at blocks of 512, 64, 1024 and 333, and with every control at its minimum and its maximum. Then a loop back in the middle of a note, a stop in the middle of a note, a release while a note sounds and a bypass (with a note played in while bypassed) must each leave nothing on, and a changed control must survive saving and loading into a second instance and play the same.

## The interface

A built plugin draws its interface with the component library in a web view, from the same files and through the same mapping as the builder's panel (`platform/PangeaWebEditor.h`, `platform/web/`; decision 77). The page is compiled into the plugin and served from memory, so nothing is loaded from the network. The rest of this section describes the shell's own editor (`platform/PangeaEditor.h`), which `--native-editor` builds in its place.

`ui.json` is the look the creator chose on the web and, once they have arranged it, the layout: one format for the web panel, this shell and the desktop app, defined in `src/lib/ui/schema.ts` (`docs/architecture.md`, "The plugin interface"). It reaches the plugin as data, never as source: `build.sh` copies it into `build/generated/` (an empty object when the project has none) and CMake compiles its bytes in with `juce_add_binary_data`. The editor reads them when it opens, with `juce::JSON::parse`, and checks every field again (`platform/PangeaUi.h`), whatever the checks before the build said. Whatever is wrong falls back on its own: a bad colour to the default colour, an unknown style to vintage, a bad layout item is skipped (its control is placed with the new ones), a bad layout gives the automatic arrangement, a bad title the plugin's name.

- The palette and the five looks (`vintage`, `minimal`, `pedal`, `playful`, `retro`) are drawn as `docs/interface-styles.md` says, with circles, arcs, lines and rounded rectangles. No `style` draws vintage. The serif is Georgia, the sans Helvetica Neue and the mono Menlo (the web has Fraunces, Inter and IBM Plex Mono). `knobStyle` is checked but no longer changes the drawing: the style decides.
- With a layout, each control's cell sits at its `x`, `y` (720 units wide; the title row sits above the layout area), at its size (`s`, `m`, `l`: `cellSize` of `src/lib/ui/layout.ts`), under its `label` if it has one (on the panel only; the host keeps the parameter's own name), and not at all when `hidden`. Items are fitted as `carryLayout` fits a parent's layout: kept on the 8 unit grid and inside the panel, items naming controls this build does not have are dropped, and controls the layout does not name go in rows below.
- Without a layout, the controls are arranged in panels that follow the Faust groups, as before, in medium cells. A logic module's controls follow, those in no group side by side and each `[group:...]` in its own titled panel where its first control appears, as `logicTree` in `src/lib/logic/meta.ts` builds them.
- A control's key is the labels of the groups below the root group and its own label, joined by `/`, as `src/lib/ui/keys.ts` defines it (`Filter/Cutoff` in Poly Saw, `Time` in Tape Drift). A logic control's key is its `[group:...]` and its name (`Left hand/Accent 1` in Two Hands, `Rate` in MIDI Steps), the same key the web gets from the tree `meta.ts` builds, so a project's layout places logic controls like any other. A logic control whose key a Faust control already has is still shown, below the rest.
- A logic control is drawn by its hint (`docs/midi-tools.md`, "Controls"), in the same cell as a knob of its size, in all five looks:
  - **knob** (the default, and any style the shell does not know): a knob, as for Faust.
  - **menu:** its labels as a segmented control, one row each, when there are at most 3 (small), 4 (medium) or 5 (large) and each fits the cell; otherwise a drop-down showing the chosen label that opens the list.
  - **bars:** a vertical level bar, narrower than a knob. A click sets it where it lands, a drag moves it, a double-click resets it. With `[playhead:N]` it is lit (in the accent, with a 2 unit ring 3 units out) while display slot N shows its place among the bars of its group that share that slot, and the host is playing; the editor reads the slots 30 times a second. Several bars in a group read as a row.
  - **generate:** the number, back and forward either side (one down, one up), and Generate under it, which moves to the next number and past the last back to 1. 0 means no variation.
- Pangea's bypass is a switch at the far right of the title row in all five looks: the power sign the web panels use, filled with the accent while the plugin is in and an outline while it is bypassed. It is attached to the plugin's bypass parameter, so the host, automation and the panel stay in step. The word "Pangea" sits to its left, and the pedal's centred title gives up the same room on both sides. While the plugin is bypassed the controls are drawn at 45 per cent, as the web panels draw them, and stay usable. `pangea-render editor --set pangea_bypass=1` draws it bypassed.
- The editor draws in layout units and scales to its window. The host and the corner handle resize it at a fixed shape, from half (or the opening size, if smaller) to twice its natural size. It opens at its natural size, or smaller when that would be taller than 820 points.
- Values are typed by double-clicking them; double-clicking a knob resets it.

`pangea-render editor <out.png> [--ui <ui.json>] [--set <id>=<value>]... [--scale <n>] [--width <points>] [--play <seconds>]` draws an editor offscreen. `--ui` draws the build with another interface file, read and checked exactly as the embedded one is, so one build can be drawn in every style; `--set` gives a control a value first; `--width` resizes first; `--play` runs the processor with a playing transport first, so a logic module's playheads show. It prints what fell back and why. `tools/render-screens.sh` makes every picture in `docs/screens/` (in Pangea's own repository only), MIDI Steps in all five looks and with a layout that places its controls by key (`midi-steps-*.png`, from `docs/screens/ui/midi-steps-*.json`) and Two Hands with its own layout among them.

## Build times

The build directory is shared by every project. The plugin's name, codes and version are kept out of the JUCE module objects (CMake strips the `JucePlugin_*` identity definitions from the shared code target and puts the name on `HybridShell.cpp` alone), so after the first build only the shell source and the AU and VST3 wrappers recompile for a new project or a new version. No link-time optimisation: the bench measured 7 seconds against over 2 minutes.

Measured on this Mac on 7 November 2026 (Apple silicon, Xcode 26, JUCE 8.0.10, Faust 2.88.0; wall time of `build.sh` including install and auval, compile time in brackets):

| Build | Time |
|---|---|
| First build after `--clean` (JUCE's juceaide at configure, then every JUCE module) | 47 s (14 s configure, 33 s compile) |
| Same project again, nothing changed | 10 s (5 s compile) |
| Same project, new version number | 28 s (19 s compile) |
| Another project of the same kind | 20 s (13 s compile) |
| First build of the other kind (effect after instrument, or the reverse): that target's JUCE modules compile once | about 45 s |
| `--verify` the first time: `pangea-render` compiles its own copy of the JUCE modules | about 30 s more, once |
| A MIDI tool after another project, with `--verify`, `--install` and auval on both plugins (8 November: MIDI Steps 21 s, Two Hands 23 s; its two targets' JUCE modules compile once, in about half a minute) | 21 to 24 s |

What recompiles for a new version or project: `HybridShell.cpp` (7 to 8 s, it holds the Faust code), the AU wrapper (4 s + 2 s), the VST3 wrapper (7 s) and the VST3 manifest helper (4 s), in parallel, then the links. The details are in `PROGRESS.md`, section "Native shell".

## The source check

A shared project is untrusted code, so `check-project.sh` runs before anything compiles, with no dependencies beyond bash, awk, sed and grep (and python3, from the Command Line Tools, for `ui.json`). It is defence in depth: the server refuses to save a version that breaks these rules (`src/lib/faust/faust-rules.ts`, `logic-rules.ts`), the desktop app runs the same check in Rust, and this script runs it a third time where the compiler runs. A logic module is still native code compiled on the user's Mac, so until logic modules are sandboxed `build.sh` refuses one unless it is called with `--allow-logic`, and the desktop app passes that flag only for the user's own projects.

- `plugin.json`, when the directory has one, must pass `tools/read-plugin-json.py` (the fields above, each in its format; `kind` effect, instrument or midi). A MIDI tool also needs an `fxPluginCode` that is valid and differs from `pluginCode`, an `fxBundleId` that differs from `bundleId`, and a `logic.cpp`.
- `dsp.dsp` may not use `ffunction`, `fconstant`, `fvariable`, `foreign` or `soundfile`; may only `import` or `library` a standard Faust library by its plain name (`import("stdfaust.lib")`, `library("filters.lib")`); may not use `component`.
- `logic.cpp` may not have a line ending in a backslash (a continuation could split a directive or a word); may contain no preprocessor directive except exactly `#include "logic_api.h"`; none of the words `asm`, `__asm`, `__attribute__`, `extern`, `system`, `new`, `delete`, `malloc`, `calloc`, `realloc`, `free`, `fopen`, `popen`, `socket`, `dlopen`, `thread`, `std` (so no `std::`), `goto`, `reinterpret_cast`, `const_cast`, nor any word starting with `exec`, `pthread_` or `__builtin_`, whether in code or inside a string literal; no `[[` (attributes); no `(*` (function pointers and pointer casts); no raw string literals and no digraphs or trigraphs (`%:`, `??`), which could spell something the check would not see.
- Comments are stripped before every check by a stripper that understands string and character literals, so a comment cannot trip the check and a quote cannot hide a comment opener. String contents are checked too, so a string cannot hide a word.
- Faust runs on a copy of `dsp.dsp` inside `build/generated`, so a `.lib` file placed next to a project is never found.
- `ui.json` must be a plain file (not a link) of at most 64 KB, UTF-8, holding one JSON object in the format of `src/lib/ui/schema.ts`: `title` (1 to 60 characters after trimming), `palette` (`bg`, `panel`, `accent`, `text`, each `#rrggbb`), `knobStyle` (`round` or `arc`), optionally `style` (one of the five) and `layout` (`width` 720, `height` a whole number from 120 to 1600, at most 128 `items`, each with a `key` of 1 to 200 characters, whole-number `x` from 0 to 720 and `y` from 0 to 1600, `size` `s`, `m` or `l`, optionally a `label` of 1 to 40 characters and `hidden` true or false). Lengths are counted in code points, as zod counts them. Unknown fields are allowed. `tools/check-ui-json.py` (run with `python3 -I`) prints one line per problem; the desktop app runs the same rules in Rust before it writes the file. A run of the real `projectUiSchema` over the 48 example, check and edge case files agreed with it on every one (`PROGRESS.md`).

`tools/test-check-project.sh` proves the good examples pass (the six examples with their `ui.json`, `midi-steps` and `two-hands`, `checks/good-comment` with every forbidden word inside comments, `checks/good-ui` with every field of the interface used) and the bad ones are refused (`bad-project` with an `ffunction` and an `#include <cstdio>`, `checks/bad-continuation` with `#inc\` + newline + `lude <cstdio>`, `checks/bad-string` with `malloc` inside a string, `checks/bad-attribute` with `[[gnu::noinline]]`, and for `ui.json` one case per kind of problem in `checks/bad-ui-*` plus generated ones: over 64 KB, 129 items, a link, a lone surrogate, bytes that are not UTF-8, `NaN`; and for a MIDI tool's `plugin.json` a missing, invalid or repeated `fxPluginCode`, a repeated `fxBundleId`, an unknown kind and a missing `logic.cpp`), each for the reason it names.

## Running outside the GUI session

`auval` asks the per-user `AudioComponentRegistrar`, which lives in the user's GUI launchd session. A shell that is not in that session (an SSH login, an agent, a cron job; `launchctl managername` prints `Background` instead of `Aqua`) reaches the system registrar instead, which knows only Apple's own components, so every third-party Audio Unit looks missing. `build.sh` detects this and runs `auval` through `tools/run-in-gui-session.sh`, which starts the command as a one-off job in `gui/<uid>` with `launchctl bootstrap` and collects its output. The desktop app is a GUI app and needs none of this.

## Known limits

- The web view panel, which a build has unless `--native-editor` is given: a logic module stopped for running too long shows no message on it; nothing is shown in its place if the page cannot draw; its colours need macOS 13.1 (the library's stylesheet uses `color-mix`, and the build still allows macOS 12.0); a layout made on the builder's older panel (`ui.layout`) is not used, only the library's own arrangement; WebKit's processes take about 200 MB while a panel is open; and `--verify`'s picture of it is blank, because a web view draws nothing off screen (`docs/decisions.md`, decision 77).
- The shell's own editor draws `ui.json`'s look and layout natively; it is not the web panel itself, so the two read the same but are not identical to the pixel (`docs/interface-styles.md`). A highlighted control (Tune) has no meaning in the plugin and is not drawn.
- Faust is run with `-ftz 1`, not the `-ftz 2` the architecture note names: Faust 2.88.0's `-ftz 2` output takes the address of a negated temporary (`&-fTemp7`), which clang refuses. Both flush denormals to zero; `-ftz 1` compares against `FLT_MIN` instead of reading the bits. The shell also sets the CPU's flush-to-zero mode for every block, so this is belt and braces.
- Controls inside a group come in the order the Faust compiler reports them, which is alphabetical unless the labels carry `[0]`, `[1]` ordering prefixes.
- Faust versions: the browser uses faustwasm 0.20.0 (libfaust 2.90.19) and the native build the Homebrew release 2.88.0, as `library/faust-versions.json` records. `build.sh` warns when the installed `faust` differs from that file and writes both versions into its JSON line. The desktop app carries Faust 2.88.0 (`desktop/scripts/build-faust.sh`), so its builds match `native.faust`; the browser's 2.90.19 is still newer.
- Builds are unsigned apart from the linker's ad-hoc signature. That is fine on the user's own machine: macOS loads locally built, ad-hoc signed plugins, and Pangea builds plugins only on the machine that runs them (decision 2). Nothing here is distributed, signed or notarised.
- Pitch bend, mod wheel and other MIDI controllers are not routed to Faust controls yet. Logic modules receive the transport, not MIDI; a MIDI tool drops the MIDI it is sent.
- A MIDI tool's display slots light the playheads in the editor only; hosts see the notes, not the slots.
- One build at a time: the build directory is shared.
- A logic module's step budget stops a call that runs too long or too deep, not a write past the end of an array: a module is still native code in the host's process, so the desktop app builds one only for the member's own projects (decision 46, `docs/midi-tools.md`).
- `mydsp_poly` prints a line to stderr when it steals a voice. Harmless, but not silent. It prints one too for a note off it cannot match, which a bypass makes an everyday case, so the shell asks it for a note off only when a voice holds the pitch.
- The bypass has been run in no DAW. How each host treats its own bypass button is known from other developers' reports only: Logic's and Live's buttons are said to stop calling a plugin and tell it nothing, so there the panel's switch and the host's button are two things, while Cubase and Studio One are said to drive the plugin's parameter.
- An Audio Unit is loaded only by `auval`, after an install. The other checks play the processor itself and the built VST3. So what the Audio Unit wrapper does with the bypass parameter is read from JUCE's code, and `auval` has not yet been run on a plugin that has it.
- With the web panel, a control that the host moves while the plugin's window is hidden shows its old value when the window comes back, until it moves again. A page that comes back is told the bypass again, and not the controls. This was so before the bypass.
- The model is not yet told to write no bypass of its own. A plugin whose code has a control named Bypass shows two: its own among its controls, and Pangea's in the title row.
- A bypassed plugin's code runs on, so it takes the processor time it takes when it is in. A plugin with a fixed delay hidden in its Faust code (a lookahead) is late by that much when it is in and not when it is bypassed: the shell reports no latency and does not delay the dry sound to match.
- An instrument's effect section, and a voice's release, ring on unheard while bypassed, so a bypass taken off inside a tail lets the rest of the tail through, as in the builder.
- A control that an instrument's voice and its effect section both read is one parameter here and sets both. In the builder it moves in the effect only: faustwasm's node sends a value whose address the effect has to the effect alone, so the voices keep the default. None of the 29 instruments Pangea had written when this was measured has such a control; Dub Keys has one (Tone) so that the shell is tested with it.
- An effect section that does not compile is left out and the build still succeeds, because the builder plays such an instrument without it. The build's last line says `"effectSection": "left out"`; nothing on the site says so yet.
- An effect section that gives more than eight channels is left out too, and the build says so, though the site's compile accepts one (it reports sixteen outputs for an effect that gives sixteen). A plugin carries eight channels at most.
- The shell is built on JUCE 8, which is under the GNU Affero General Public License version 3 or JUCE's own licence, and the shell is published under the GNU Affero General Public License, version 3 or later: see `LICENSE` and `NOTICE` (decision 127).
- The sidechain has been run in no DAW, and `auval` has not seen a plugin with one: an Audio Unit is loaded only after an install. What JUCE's Audio Unit wrapper does with the second bus (an input element that is always there, cleared while nothing is routed to it) is read from its code. The steps for Logic, Live, Bitwig and Reaper are in `docs/sidechain.md`.
